# Wiggle Web 미결정 항목

## 2026-10-03 PDF 개별 글자 수정 범위 (응답 대기)

사용자 요청 원문: “직접 넣었을 때도, 그림책 수정이 가능해야해. 실제로 그림책 만들 때처럼 기능들 똑같이 활용할 수 있게 해 줘.”

확인 질문: “PDF 수정은 어느 범위가 필요하신가요? 현재 저장된 PDF는 각 쪽이 한 장의 이미지라서, 원본을 보존하면서 글·그림을 추가하고 크기·위치·쪽 순서·양식을 편집하는 기능은 구현할 수 있습니다.”
선택지: “원본 위에 글·그림 추가와 페이지 편집이면 돼” / “PDF 안의 기존 글자 자체도 고쳐야 해”.
답변 전까지 기존 PDF를 이미지로 보존하는 동일 편집기 작업을 진행한다. 개별 글자 분해나 OCR로 기존 작품을 대체하지 않는다.

## 2026-10-31 그림책 주문 운영 전에 정할 것 (응답 대기)

- **가격과 입금 계좌**
  - 관리자 화면에 1권 가격, 추가 쪽 가격, 배송비, 무료 배송 권수, 부가세 포함 여부, 은행, 계좌번호, 예금주, 상호를 넣어야 주문을 받는다.
  - 사업자등록번호·주소·연락처는 견적서 공급자 칸에 넣을 값이다.
- **세금계산서·현금영수증**: 학교 결재에 세금계산서가 필요한 경우가 많다. 발행 요청을 받을 칸과 절차가 필요한지 정해야 한다.
- **제작 연결**
  - 입금이 확인된 주문을 스위트북 발주로 잇는 단계는 아직 운영자가 손으로 한다. 기존 「제작 요청」이나 제작사 포털을 쓴다.
  - 주문 뒤 학생이 책을 고치면(revision) 주문 당시 판을 쓸지 정해야 한다. 주문 기록에는 당시 revision이 남아 있다.
- **그림 잠금의 영향**: 손들기와 선생님 메시지 받기는 그림판 안에만 있어서 지금 학생에게 보이지 않는다. 그림책 화면에 다시 둘지 정해야 한다.

## P-001 학생을 실제로 구분하는 운영 방식 — 2026-09-07 확정, `product-decisions.md`로 이동

교사가 학급을 만들 때 명단(번호 + 실명)을 직접 입력하고, 학생은 수업 코드나 QR로 들어와
자기 참여 코드 6자리로 자기 창을 연다(2026-09-09: 번호 + 그림 비밀번호를 참여 코드로 대체). 명단은 학생 화면에 보여 주지 않는다.
확정 내용과 이유는 `product-decisions.md`의 `학생 입장과 기록` 7번에 있다.

### 법적 검토 메모 (2026-08-31, 사용자 질문에 대한 분석 — 법률 자문 아님)

사용자 질문 원문: "학급 반 번호를 입력하게 해서 아이들을 판단하려고 하는데 법적으로 문제가 없을려나"

- 반 번호는 단독으로는 식별 불가하지만, 개인정보보호법의 개인정보 정의는
  **"다른 정보와 쉽게 결합하여 알아볼 수 있는 정보"**를 포함한다.
  이 기능의 목적 자체가 교사가 명부와 결합해 아이를 특정하는 것이므로
  "서버에 학교명이 없으니 익명"이라는 방어가 약하다.
- 초등 1~3학년은 전원 **만 14세 미만**이다. 개인정보 처리로 판정되면
  법정대리인 동의 + 동의 확인 절차가 필요해질 가능성이 높고,
  "설치·가입·동의서 없이 수업 코드로 시작"이라는 제품 포지션이 무너진다.
  개인정보처리방침의 "학생은 익명으로 참여" 문장도 거짓이 된다.
- 개인정보보호위원회는 아동 데이터에 엄격한 해석을 적용하는 추세다.
- **결론: 현장 검증(P-005) 전에 결정하지 않는다.** 검증 항목에
  "교사가 실제로 학생 구분에 곤란을 겪는가"가 이미 있다(PRD §9.4).
  검증 후에도 필요하면 도입 전 개인정보 전문 검토를 받는다.
- 중간 경로: 교사가 종이 명부에 `여우화가 = 12번`을 적는 방식은
  서버가 아무것도 수집하지 않아 법적 변화가 없다. 1차 검증에서는 이걸 안내한다.

### 추가 질문 (2026-09-07 — 이름까지 수집하는 안)

사용자 질문 원문: "반 번호 이름으로 수집해서 진행하기로 했어, 법적으로 문제가 없는건가?
선생님한테 물어보니까 학기초에 개인정보제공동의서를 받는다고하는데, 흠 괜찮을려나?"

분석 (법률 자문 아님):

- 이름+반 번호는 결합 논쟁 없이 개인정보다. 만 14세 미만이므로 법정대리인 동의가 필요하고,
  아이 본인·교사 동의로 대체할 수 없다(개인정보보호법 22조의2).
- 학기초 동의서가 유효하려면 문면에 ①수집 항목(이름·반·번호) ②목적(외부 교육 서비스
  이용/위탁) ③제공받는 자(운영 주체 업체명) ④보유 기간이 실제로 있어야 한다.
  학교 자체 목적으로 받은 동의의 전용은 목적 외 이용이다. **동의서 실물 확인 전에는
  "괜찮다"고 판단하지 않는다.** 검증처 3곳(학교 2·지역아동센터)마다 각각 확인해야 한다.
- 동의가 유효해도 서버에 이름이 저장되는 순간 서비스가 개인정보처리자(또는 수탁자)가 되어
  처리방침 개정·안전조치·유출 통지·위탁계약 의무가 생기고, 랜딩 문구
  "학생 이메일·실명 없이 안전하게"와 제품 불변 원칙(실명 금지)을 뒤집게 된다.
- 유지 권고: 위의 중간 경로(교사 오프라인 명부 매핑 `토끼화가 = 3반 12번`)로 1차 검증을
  진행하고, 그래도 부족하면 동의서 실물 + 개인정보 전문 검토를 거쳐 도입을 결정한다.

### 부분 결정 (2026-09-07): "그럼 일단은 반 번호로만 진행하자"

> ⚠️ 2026-09-09 병합에서 대체됨: 아래의 "선택 입력 반 번호"는 같은 날 다른 세션에서 확정된
> **교사 명단(번호+실명) 모델**로 대체돼 구현이 제거됐다(`product-decisions.md` 학생 입장 7·8항).
> 두 경로가 공존하면 같은 아이가 명단 자리와 자기 등록 프로필로 갈라지기 때문이다.

- 이름 없이 **반 번호(출석번호)만 선택 입력**으로 수집한다 — 확정 결정 「학생 입장과 기록」 16항.
- 이름 수집 여부는 계속 미결이다. 열려면 검증처별 학기초 동의서 실물 확인 + 전문 검토가 선행 조건.

## P-005 커리큘럼 현장 검증 설계 (2026-08-30 신설)

### 배경

테스트할 학교와 지역아동센터 2곳이 확정됐다. 사용자가 밝힌 최대 우려는
"실제 클라이언트가 쓰지 않는 기능이 많다"와 "교구 안의 커리큘럼이 실제 수업에서 쓰일지 의문"이다.
`docs/ux-market-audit-2026-07.md`에 1~2학년 5명 무개입 사용성 테스트 프로토콜
(과제 6개, 성공 기준: 주요 과제 80% 이상을 중립적 힌트 1회 이하로 완료)이

## P-013 도구 막대 접기 손잡이가 도화지를 덮는다 (2026-09-23 신설, 실측으로 발견) — 사용자 보류

## P-014 몽그리가 뜬금없는 짐작을 한다 (2026-09-26 신설, 운영 제보) — 2026-09-26 종결: 사용자 "가로 가자", `product-decisions.md` 학습 과정 4항

사용자 제보 원문: "너무 뜬금없는대답을 한다고 하기도하고, 처음에 추측을 할때, 집을 그리면, 다른걸로 추측해버린다"

### 원인은 둘이고, 서로 곱해진다

**① 몽그리가 그림을 제대로 못 본다 (기술)**

- AI에 보내는 이미지는 `imageData(canvasRef.current, 1024)`다 — **그린 칸을 자르지 않고** 도화지 전체를 보낸다.
  넓은 도화지는 span 3(화면 세 장)이라 대부분이 흰 여백이다.
- 게다가 `lib/openai-coaching.ts:313`이 `detail: "low"`라 OpenAI가 긴 변 **512px**로 다시 줄인다.
- 실측(2026-09-26, 헤드리스 크롬): span 3 도화지에 340×290 크기로 집을 그리면
  모델이 받는 그림은 **512×96**이고 그 안에서 집은 **57×48px, 넓이의 5.6%**다.
  그린 칸만 잘라 보내면 **512×437px — 9배**가 된다.
- 같은 문제를 썸네일·완성본에서는 이미 풀어 두었다. `documentImage()`가 span>1이면 `contentBounds`로
  그린 칸만 잘라 낸다("흰 여백이 대부분이라 … 아이 그림이 1/3 크기로 들어간다"). **AI 경로만 그 방식을 안 쓴다.**

**② 일부러 빗나가게 시킨다 (설계)**

`STORY_INTERPRETATION_INSTRUCTIONS`(같은 파일 33~34행):

> "일부러 덜 구체적으로 짐작한다. 정확한 사물 이름 대신 갈래로 말하거나 **두 번째로 그럴듯한 읽기를 고른다.**"

이것은 `학습 과정 4항 틀리는 해석자`(Weng et al. 2025)를 그대로 구현한 것이다. 버그가 아니다.
다만 그 설계의 전제는 **"그럴듯하게 살짝 빗나간 짐작"**이다(우산 ↔ 자전거 바퀴처럼 형태가 닮은 것).
①로 첫 짐작이 이미 틀리면, 거기서 다시 두 번째 읽기를 고르므로 **완전히 무작위**가 된다.
아이가 받는 인상은 "몽그리가 내 그림을 보고 다르게 읽었네"가 아니라 "몽그리가 아무 말이나 하네"다.

### 결정이 필요한 것

①은 명백한 결함이라 고치는 데 결정이 필요 없다(비용·지연은 확인 필요). ②는 제품 결정이다.

- **(가) 확신도로 갈린다 — 2026-09-26 사용자 채택.** — 확실히 알아보면 맞게 짐작하고 "맞아?"라고 확인한다.
  애매할 때만 갈래로 말한다("동물처럼 보이는데?"). 근거 발화를 끌어내는 목적은 유지하면서
  아이가 "몽그리가 못 알아본다"고 느끼지 않는다. 코칭 쪽에는 이미 `uncertain` 필드가 있어 개념이 있다.
- **(나) 빗나가되 가까이** — 형태가 닮은 것으로만 빗나간다. 원 설계(우산↔자전거 바퀴)에 가장 충실하지만
  "닮은 것"을 모델이 고르게 하기가 어렵고, ①을 고쳐도 여전히 아이가 틀린 말을 먼저 듣는다.
- **(다) 짐작을 버린다** — "무엇을 그렸는지 말해 줄래?"로 바꾼다. 가장 안전하지만
  학습 과정 4항의 교육 설계를 포기하는 것이므로 그 근거를 뒤집는 결정이 된다.

### 남은 위험

- `detail`을 올리면 토큰·비용·지연이 는다. 그린 칸만 잘라 보내면 이미지가 작아져 상쇄되는 부분이 있다 — 실측 필요.
- 로컬에 `OPENAI_API_KEY`가 없어 실제 응답 품질은 아직 비교하지 못했다. 고친 뒤 실제 호출로 확인해야 한다.
